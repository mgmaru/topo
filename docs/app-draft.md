# Topo — IT用語の地図アプリ コンセプト（2026-10-13時点）

## 0. 名前（仮）

**Topo**（トポ）。地形図（topographic map）の略で、登山で使う地図の呼び名でもある。「自分の現在地と、まだ登っていない場所がわかる」という使い方のイメージに合わせて仮採用。正式採用時は同名サービス・リポジトリ名の衝突を確認する。

## 1. 背景・解決したい悩み

日々アプリを開発しているにもかかわらず、IT用語を自分の言葉で説明できない。これにより次の問題が生じる。

- 技術面接で不利に働く
- 業務での意思疎通・効率が落ちる
- 設計力が上がらない（トレードオフを語れない）

面接や設計で問われるのは「定義を言えるか」ではなく「なぜそれを選ぶのか（トレードオフ）を語れるか」である。アプリはここに焦点を当てる。

## 2. アプリの目的

1. IT用語を地図として整理し、頭の中の知識を構造化する
2. 用語の基本的な説明に加え、要件ごとに「なぜそれを選ぶのか」を説明できるようにする
3. 類似技術との比較（同じ部分・違う部分）ができるようにする
4. 技術どうしのつながりを説明できるようにする
5. 自分の技術力を客観的に見つめられるようにする
6. **自分の知識の穴がわかるようにする**

## 3. 基本方針

### 「読む」アプリにしない
きれいな地図や比較表を眺めるだけでは説明できるようにならない。中心の流れは次の形にする。

> 自分で説明を書く → 抜け・誤りを指摘される → 地図に反映される

AIを使う場合は答えを出す役ではなく、面接官役として突っ込む役にする。

### 地図は「全体」から作らない
網羅を目指すと終わりが見えない。自分が実際に触った技術（HTTP、TCP電文、Tauri、PostgreSQL など）を起点に広げる。経験に紐づいた説明になるため面接でも強い。

### 小さく検証してから広げる
地図の可視化は見た目が魅力的だが核心ではない。まずは1分野（ネットワークかDB）、用語20〜30個で「説明を書く → 指摘される → 段階が上がる」が効くかを試す。

### 「自分の地図」を作る — ノードは共有、線は個人
Topo が何であるかを決める最も重要な方針。

人によって知識の身につけ方、知識のつなげ方は違う。経験・体験が違い、学ぶ順番も違う。TCP電文から入った人と Web制作から HTTP に入った人では、「ネットワーク」というノードにつながっている線がまったく違う。前者は TCP が先にあって HTTP が「その上に乗るもの」、後者は HTTP が先にあって TCP が「あとから掘ったら出てきたもの」になる。どちらも正しく、どちらも面接で語れる説明になる。語れるのは、その線を自分で引いたからである。

roadmap.sh のようなロードマップは「正しい順番」を1本に決めて全員にそれを歩かせる。Topo はそうしない。

- **ノード（用語そのもの）は共有できる**: 「PostgreSQL」は誰が見ても PostgreSQL
- **線（つながり）は個人のものである**: 「PostgreSQL と Docker がなぜ自分の中でつながっているか」は、自分の開発経験があって初めて引かれた線
- 地図の広さはみんな同じ素材から作れても、地図の形は人の数だけある。**Topo における「自分の地図」とは、この線の集合のこと**

この方針から導かれること:

- **参照地図との両立**: 参照地図（求人票・roadmap.sh 等）は「どんなノードが存在するか」を教えるだけで、「どうつなぐか」は押しつけない。穴の検出にはノードの有無だけを使い、構造は自分のものを保つ。これで「自分の地図を作る」と「穴を見つける」は両立する
- **学習履歴も経路**: 開発経験がプロダクトごとの経路なら、学習の履歴も「どの順番でノードを訪れたか」という時系列の経路。見返すと「いつも実装から入って概念をあとから埋める」のような、自分の知識の身につけ方そのものが見える。次に何を学ぶかの判断材料になる
- **自分の線が間違っていることもある**: 経験から来た理解は強い反面、たまたまそのプロジェクトではそうだっただけのことを一般法則だと思い込むことがある。線を引くときに「なぜつながるのか」を一言書かせ、それに突っ込みを入れる。**構造は個人のもの、検証は外からの目で**、という分担にする
- **将来の拡張（他ユーザーがいる場合）**: 「同じノードを、別の人はどうつないでいるか」を見比べられる機能。正解を押しつけるのではなく、自分と違う線の引き方を見て気づきを得る。一本道のロードマップにはない価値

## 4. データモデルと見せ方の分離

迷いの正体は「地図か模擬面接か」というUIの二択ではなく、「データを1つにするか」「見せ方を1つにするか」の混在だった。

- **データは1つ**: 定義・つながり・選定理由・自分の経験は、すべて同じノード（技術）に紐づく情報
- **見せ方は複数**: 地図が主画面。模擬面接はそのデータを「問いの形で引き出す」1つのモード
- 面接で答えられなかった技術が地図上で浮き彫りになる、という連携が同じデータだからこそ可能

## 5. 地図の構造

### 広さと深さ
- 広さ = IT技術の広がり
- 深さ = その技術の理解の深さ

構想としては「2次元の地図に深さを加えた3次元」。ただし**実装は2D＋階層**にする。文字どおりの3D表示は操作が難しく、文字が読みにくく、作るのも大変で、本来の目的から遠ざかる。

深さは「ズーム」「断面図」として扱う。

- 遠景: カテゴリ・技術名のみ
- ズームすると層が開く: 定義 → 比較 → 選定理由 → 自分の経験

### 開発経験 = 地図上の経路
1つのプロダクトは複数の技術を通る1本の線として描ける（例: スクレイピング → Python → PostgreSQL → Docker → …）。

- 面接で語る「開発経験」はこの経路そのもの
- 「なぜその経路を選んだのか（別の道もあったのに）」が選定理由の説明になる
- 経路どうしを比べると得意・未経験領域が見える
- 地図でしか表現できない価値であり、差別化の核

### 層（レイヤー）
ノードは複数の層を重ねて表示できるようにする。

- 一般知識の層（定義・比較・選定理由）
- 自分の経験の層
- 期待される層（後述、知識の穴の検出用）

経験の層だけを表示すると自分の地図が小さく偏っていることが見え、客観視につながる。

### つながりの種類
線に種類を持たせ、表示を切り替えられるようにする。区別しないとノード増加時に毛糸玉になる。

- 依存関係
- 代替関係
- 上位・下位概念
- 同じプロダクトで一緒に使った（経路）

## 6. 技術力の客観視（段階の定義）

自己申告だけだと甘くも厳しくもなる。段階を定義し、説明の質を判定材料にする。

1. 名前を知っている
2. 一言で説明できる
3. 類似技術と比較できる
4. 要件から選定理由を言える
5. 実務で使った

証拠に基づいて段階が決まるようにする。

- 説明を書いていないノード → 未確認
- 書いたが指摘が多いノード → 浅い

## 7. 知識の穴の検出

### 本質的な難しさ
自分で作った地図には、自分が知らない場所は載らない。穴を見つけるには「本来あるべき地図」（参照地図）が別に必要。

### 穴の種類
| 種類 | 地図上の見え方 | 検出に必要なもの |
|---|---|---|
| 存在すら知らない技術 | 地図に載っていない | 参照地図（外部） |
| 名前は知っているが説明できない | ノードはあるが浅い | 説明の証拠 |
| 個々は知っているが関係を説明できない | 線が引けない | 参照地図のつながり |
| 業務で使っているのに理由を言えない | 経験の層にはあるが選定理由の層が空 | 層の重ね合わせ |

4つ目は当初の悩みそのもの。経験の層と知識の層を重ねることで可視化できる。

### 参照地図の素材（バックエンド・インフラ志望向け）
- 求人票の必須スキル欄
- roadmap.sh のバックエンド／DevOps ロードマップ
- 技術面接の頻出質問集
- AWS SAA の試験範囲

最初は1つの求人票を参照地図にするだけで十分。

### 穴を全部埋めようとしない
参照地図を重ねると穴は大量に見える。「全部覚えなければ」で止まらないよう、優先度の仕組みを最初から入れる。

- 自分の経路（開発経験）に隣接する穴を優先する（面接でその経験を語ると聞かれやすい）
- 遠くの穴は「今は知っている必要がない」と明示する
- どの穴を無視してよいかまで示すことが、使い続けられる条件

## 8. 差別化

既存の代替手段: roadmap.sh、Obsidianのグラフ表示、Anki等の暗記カード、ChatGPTに直接聞く。

差別化の中心:
- 「要件 → 選定理由」の層
- 同じ軸で比較できる構造
- 開発経験を経路として地図に描ける
- 参照地図との差分による穴の可視化と優先度づけ

## 9. 副次的な価値

アプリを作る過程で「この技術とこの技術の関係は何か」を定義していく作業そのものが、悩みの解決になる。検証で効果を実感できれば、それ自体がポートフォリオでの説得力になる。

## 10. 検討事項

### 10.1 何を Atomic（最小単位・ノード）にするか
最も根本的な論点。ここが曖昧だと地図全体がぶれる。

- **「1つの技術」の粒度はどこか**
  - 例: 「HTTP」「HTTP/2」「REST」「HTTPS」は別ノードか、同じノードの深さ違いか
  - 例: 「PostgreSQL」（製品）と「RDB」（概念）と「SQL」（言語）は別ノードか。製品・概念・言語・プロトコル・手法を同列に置くのか、種別を持たせるのか
  - 例: 「Docker」と「コンテナ」と「Docker Compose」をどう分けるか
- **候補となる単位**
  - 技術・製品（PostgreSQL、Docker）
  - 概念（トランザクション、冪等性、CAP）
  - 要件・課題（「同時書き込みを安全にしたい」）
  - 問い（面接で聞かれる1問）
- **概念をノードにしないと「つながり」が説明できない問題**
  - 「PostgreSQL と MySQL の違い」を語るには「トランザクション分離レベル」「レプリケーション方式」のような概念ノードが必要になる
  - 一方、概念を全部ノードにすると数が爆発し、地図が毛糸玉になる
- **暫定案（要検討）**: ノード = 「面接で単独の質問になりうる単位」。これより細かいものはノード内の属性（深さの層）として持つ

### 10.2 ノードの種別とバージョン
- ノードに種別（製品／概念／プロトコル／言語／手法／ツール）を持たせるか
- バージョン（HTTP/1.1 と HTTP/2、Python 2 と 3）をノードに含めるか、属性にするか
- 一般名詞（RDB）と固有名詞（PostgreSQL）の関係を「上位・下位概念」の線で表すのか、階層構造として表すのか

### 10.3 「要件」をどう表現するか
「要件ごとになぜそれを選ぶのか」が核だが、要件をデータとしてどう持つかは未定。

- 要件をノードにして技術と線でつなぐ（例: 「低レイテンシ」→ Redis）
- 要件をノードの属性（選定理由のテキスト）として持つ
- 比較表の軸として持つ（同じ軸で比較できる構造にするなら、軸＝要件になる）
- 要件が決まると「比較の軸」も決まるため、10.1 と並んで早めに決める必要がある

### 10.4 「つながり」の種類と方向
- 線の種類をいくつに絞るか（依存／代替／上位下位／同一経路、で十分か）
- 方向を持たせるか（依存は方向あり、代替は方向なし）
- 線自体に説明（なぜつながるのか）を持たせるか。持たせると「関係を説明できる」目的に直結するが、入力コストが上がる
- 「ノードは共有、線は個人」の方針（3章）に従うなら、線の説明は本人が書く前提になる。線を引く＝「なぜつながるのか」を一言書く、を必須にするか

### 10.5 「経験」の単位
- 経路の単位は「プロダクト1つ」か「機能1つ」か。1プロダクト内で技術選定が複数回起きる場合、機能単位のほうが選定理由と対応しやすい
- 業務（守秘義務あり）の経験をどこまで書くか。技術名と選定理由だけなら書けるか
- 「触った」と「選定した」を区別するか（保守で触っただけの技術は経験の層に入るか）

### 10.6 段階（深さ）の判定方法
- 段階を上げる証拠を何にするか（自分で書いた説明／AIの指摘の数／模擬面接の結果／時間経過による減衰）
- 判定者を誰にするか（自分／AI／他人）。AIに任せる場合、AIの指摘の質をどう担保するか
- 段階は上がるだけか、下がることもあるか（時間が経てば忘れる。下がる仕組みがないと地図全体が緑になる）

### 10.7 説明の中身を誰が用意するか
- 自分で書く: 学習効果は最大だが、参照地図側の説明まで自分で書くのは非現実的
- AIに生成させる: 参照地図側はAI、自分の層は自分で書く、という分担が現実的か
- 他ユーザーと共有する: OSS化・公開する場合の論点。個人の経験の層は共有できないので、共有するのは一般知識の層だけになる
- 「AIが書いた説明」と「自分が書いた説明」を視覚的に区別する必要がある
- 「ノードは共有、線は個人」の方針（3章）に沿うと、分担の自然な線引きは「ノードの定義＝共有・AI生成可」「線の説明・経験・選定理由＝本人が書く」になる

### 10.8 参照地図の取り込み方法
- 求人票・roadmap.sh・試験範囲をどの形式で取り込むか（手入力／AIで構造化／既存のロードマップデータの流用）
- 複数の参照地図を重ねるか、1つに絞るか
- 参照地図とのノード名の揺れ（「DB」「データベース」「RDB」）をどう吸収するか

### 10.9 データの保存形式と連携
- 専用DBか、Markdown＋frontmatterのようなテキストファイルか
- テキストファイルなら Obsidian 等の既存ツールとの併用ができ、LLMにも渡しやすい
- 読書メモの体系（疑問ファースト）との連携をするか
- ローカル完結か、サーバーを持つか

### 10.10 実装形態と可視化
- デスクトップアプリ（Tauri）か Web か。マルチOS対応の方針との整合
- グラフ描画ライブラリの選定（ノード数が数百になったときの性能・操作性）
- ズームによる層の展開をどう実装するか（UIとして最も作り込みが必要な部分）
- 最初の検証段階では可視化を作らず、テキストだけで回すか

### 10.11 最初の検証範囲
- 分野: ネットワーク or DB
- 規模: 用語20〜30個
- 検証したいこと: 「説明を書く → 指摘される → 段階が上がる」が実際に効くか
- 可視化なしでも効果が出るなら、地図はあとから乗せればよい
